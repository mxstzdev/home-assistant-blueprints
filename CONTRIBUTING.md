# Contributing

Thanks for helping out. Bug reports and ideas go to
[issues](https://github.com/mxstzdev/home-assistant-blueprints/issues); changes go through
pull requests against `main`.

## Repository layout

```text
blueprints/
  <domain>/                 # automation | script
    <name>/
      <name>.yaml           # the blueprint
      README.md             # usage and inputs
      CHANGELOG.md          # generated by release-please, do not edit
      tests/
        <domain>.yaml       # sample usage(s) for CI validation
scripts/                    # CI helpers, also runnable locally
```

## Adding a blueprint

1. Create `blueprints/<domain>/<name>/<name>.yaml`. `<name>` is lowercase `snake_case`.
2. Declare the oldest supported Home Assistant version:

   ```yaml
   blueprint:
     homeassistant:
       min_version: "2025.1.0"
   ```

3. End the `description` with the version line. release-please keeps it up to date;
   start it at `0.0.0` until the first release:

   ```yaml
     description: |
       What the blueprint does.

       **Version:** 0.0.0 <!-- x-release-please-version -->
   ```

4. Add `README.md` (usage, inputs) next to the blueprint. It starts with these badges,
   each on its own line:

   ```markdown
   # <Blueprint name>

   [![Version](https://img.shields.io/badge/version-0.0.0-blue)](CHANGELOG.md) <!-- x-release-please-version -->
   [![Home Assistant](https://img.shields.io/badge/Home%20Assistant-%E2%89%A5%202025.1.0-41BDF5?logo=homeassistant&logoColor=white)](https://www.home-assistant.io/)
   [![Import](https://my.home-assistant.io/badges/blueprint_import.svg)](<import URL, see step 7>)
   ```

   - **Version** is updated by release-please on each release. Keep the marker comment on
     that line and nothing else versioned on it.
   - **Home Assistant** must match `min_version` as `X.Y.Z`; CI fails when it does not.
     Update it in the same commit that changes `min_version`.
5. Add `tests/<domain>.yaml` with at least one usage of the blueprint. Reference it as
   `mxstzdev/<name>.yaml` and fill every required input. For an automation:

   ```yaml
   - alias: Sample
     use_blueprint:
       path: mxstzdev/<name>.yaml
       input:
         motion_sensor: binary_sensor.hallway
   ```

   For a script, the file is a mapping of script ids instead of a list.
6. Register the blueprint in `release-please-config.json`:

   ```json
   "packages": {
     "blueprints/automation/<name>": {
       "component": "<name>",
       "extra-files": [
         { "type": "generic", "path": "<name>.yaml" },
         { "type": "generic", "path": "README.md" }
       ]
     }
   }
   ```

7. Add a row to the table in [README.md](README.md). The import badge URL is:

   ```text
   https://my.home-assistant.io/create-link/?redirect=blueprint_import&blueprint_url=https%3A%2F%2Fgithub.com%2Fmxstzdev%2Fhome-assistant-blueprints%2Fblob%2Fmain%2Fblueprints%2F<domain>%2F<name>%2F<name>.yaml
   ```

## Validation

Every pull request and push to `main` runs:

- **yamllint** over the whole repository (`.yamllint`).
- **check_config** for each blueprint, once against its declared `min_version` and once
  against the current stable Home Assistant release. The blueprint and its
  `tests/<domain>.yaml` are loaded into a minimal configuration inside the official
  container image, so schema errors, invalid triggers, conditions or actions, missing
  inputs, and features newer than `min_version` all fail the build.

The stable check also runs weekly to catch breaking changes in new Home Assistant releases.

Run it locally (requires Docker):

```sh
scripts/validate-blueprint.sh blueprints/automation/<name> min
scripts/validate-blueprint.sh blueprints/automation/<name> stable
scripts/validate-blueprint.sh blueprints/automation/<name> 2025.6.0
```

Without Docker, point `HA_PYTHON` at a Python interpreter that has the `homeassistant`
package installed; the version argument is then only checked against `min_version`.

## Commits and releases

Releases are managed by [release-please](https://github.com/googleapis/release-please)
in manifest mode. Each blueprint folder is its own package:

- Commits touching a blueprint folder are attributed to that blueprint only.
- release-please opens one release pull request per blueprint. Merging it bumps the
  version line in the blueprint and the version badge in its README, updates its
  `CHANGELOG.md`, and creates the tag
  `<name>-X.Y.Z` with a GitHub release.
- Versions follow [SemVer](https://semver.org/): `fix:` bumps patch, `feat:` bumps minor,
  `feat!:` or a `BREAKING CHANGE:` footer bumps major. The first release is `1.0.0`.

Commit messages (or squash-merge titles) must follow
[Conventional Commits](https://www.conventionalcommits.org/), for example
`feat(motion_light): add illuminance condition`.

Release pull requests opened with the default `GITHUB_TOKEN` do not trigger CI. To run
checks on them, add a fine-grained token with `contents` and `pull-requests` write access
as the repository secret `RELEASE_PLEASE_TOKEN`.
