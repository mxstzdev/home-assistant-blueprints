# Contributing

Thanks for helping out. Bug reports and ideas go to
[issues](https://github.com/mxstzdev/home-assistant-blueprints/issues); changes go through
pull requests against `main`.

## Requirements

- `make`, `bash` and `jq`
- [yamllint](https://yamllint.readthedocs.io/) for `make lint` (`pip install -r requirements.txt`)
- Docker for `make test-blueprints` (or `HA_PYTHON`, see [Validation](#validation))
- [GitHub CLI](https://cli.github.com/) (`gh`), signed in with `gh auth login`, for the
  [pull request tasks](#branches-and-pull-requests)

Run `make help` for all tasks.

## Repository layout

```text
blueprints/
  <domain>/                 # automation | script
    <name>/
      <name>.yaml           # the blueprint
      README.md             # usage and inputs
      CHANGELOG.md          # generated by release-please, do not edit
      docs/                 # optional, further documents in Markdown
      tests/
        <domain>.yaml       # sample usage(s) for CI validation
scripts/                    # helpers used by make and CI
```

## Adding a blueprint

1. Create the skeleton. `NAME` is lowercase `kebab-case` and unique across domains,
   since it is also the release tag prefix; `DOMAIN` defaults to
   `automation` and `MIN_VERSION` to `2025.1.0`:

   ```sh
   make create-blueprint NAME=motion-light DOMAIN=automation MIN_VERSION=2025.6.0
   ```

   This creates the folder above, registers the blueprint in
   `release-please-config.json`, and prints the row for [README.md](README.md). Add it
   to the table under the domain's sub-heading (`### Automations` or `### Scripts`),
   creating that sub-heading and table if this is the domain's first blueprint.
2. Replace every `TODO` in the blueprint, its README and `tests/<domain>.yaml`.
3. Keep these conventions when editing:
   - The `description` starts with the Version badge, using absolute GitHub links, since
     relative ones do not resolve in Home Assistant. The README starts with the License,
     Version and Home Assistant badges, in that order. release-please updates both Version
     badges on each release; keep the `<!-- x-release-please-version -->` comment on those
     lines. It replaces only the first version on a marked line, so the Version badge must
     stay the first versioned badge there.
   - The `description` ends with the Documentation and Changelog links (the blueprint's
     folder and its `CHANGELOG.md` on GitHub) and the Ko-fi button. Keep the `yamllint`
     comments around it, as the badge lines exceed the line length.
   - The README keeps the generated Installation (with the Import button), Updating
     and License sections. `CHANGELOG.md` is linked from the Version badge and the
     Updating section, so it needs no section of its own.
   - Longer documentation goes into an optional `docs/` folder (not scaffolded). The
     README then lists each document in a `## Documentation` section, one line per
     document with a short description, between Updating and License. Links inside
     `docs/` are relative, for example `../README.md#inputs`; the root license is
     `../../../../LICENSE` from there.
   - The README's Home Assistant badge and Requirements line show `min_version` as
     `X.Y.Z`. CI fails when the badge does not match, so change them in the same commit as
     `min_version`. The `description` has no Home Assistant badge, because Home Assistant
     itself refuses blueprints that need a newer version.
   - `tests/<domain>.yaml` uses the blueprint as `mxstzdev/<name>.yaml` and fills every
     required input. For an automation it is a list, for a script a mapping of script
     ids.
   - Do not edit `CHANGELOG.md`.
4. Run `make lint test BLUEPRINT=blueprints/<domain>/<name>`.

## Validation

Every pull request and push to `main` runs:

- **yamllint** over the whole repository (`.yamllint`).
- **check_config** for each blueprint against its declared `min_version`, the current
  stable Home Assistant release and the latest `dev` build. The blueprint and its
  `tests/<domain>.yaml` are loaded into a minimal configuration inside the official
  container image, so schema errors, invalid triggers, conditions or actions, missing
  inputs, and features newer than `min_version` all fail the build. An import round trip
  then saves the blueprint the way the Import button does and loads it again, which
  catches selector options that Home Assistant cannot read back after an import.
- **Scaffold check**: a throwaway blueprint from `scripts/create-blueprint.sh` for each
  domain must pass yamllint and check_config, so the skeleton never drifts from these
  conventions.

The checks also run weekly to catch breaking changes in new Home Assistant releases.

How each version is picked:

| Check | Runs on | Blocks |
| --- | --- | --- |
| min | the `min_version` image; left out when it equals stable | every run |
| stable | the current stable release | every run |
| dev | the latest nightly of the upcoming release | scheduled and manual runs only |

A failing dev check shows on pull requests as a warning, which leaves time to fix the
blueprint before the release.

A `min_version` that is not released yet, e.g. for a feature of the upcoming release, is
checked on the beta of that release, or on `dev` while there is no beta. That check blocks
every run, and the stable check is skipped with a warning. A `min_version` that no beta or
dev build leads to fails the build. Keep in mind that merging such a blueprint releases it,
and Home Assistant refuses to import it on any version older than `min_version`, beta and
dev builds included.

Run it locally:

```sh
make test-blueprints                                          # all blueprints, min and stable
make test-blueprints BLUEPRINT=blueprints/automation/<name>   # one blueprint
make test-blueprints HA=dev                                   # the latest dev build
make test-blueprints HA=2025.6.0                              # a specific version
```

`min` uses the `min_version` image, so it fails for a `min_version` that is not released
yet. Use `HA=beta` or `HA=dev` for those.

Without Docker, set `HA_PYTHON` to a Python interpreter that has the `homeassistant`
package installed. The installed version is then used for every run, and only compared
against `min_version`.

## Shell scripts

Scripts in `scripts/` follow the
[Google Shell Style Guide](https://google.github.io/styleguide/shellguide.html) and must
pass [ShellCheck](https://www.shellcheck.net/).

## Dependency updates

[Dependabot](https://docs.github.com/code-security/dependabot) checks the GitHub Actions
used in `.github/workflows/` and the Python tools in `requirements.txt` once a week
(`.github/dependabot.yml`). Minor and patch updates arrive as one grouped pull request,
major updates as one pull request each, since they may need workflow changes. New releases
are only proposed once they are seven days old. The commits use `ci(deps):`, so they never
trigger a blueprint release.

Actions are pinned to a full commit SHA, with the version as a comment, for example
`actions/checkout@<sha> # v5.1.0`. Dependabot updates both. Pin new actions the same way.

## Branches and pull requests

Branch names follow `<scope>/<topic>`, both in lowercase `kebab-case`:

- `<scope>` is the blueprint name for changes to one blueprint, for example
  `area-heating-control/sync-trv-setpoints`. Otherwise it is one of `ci`, `docs`, `repo` or
  `scripts`, for example `scripts/github-pr`.
- `<topic>` names the change in a few words.

The pull request tasks wrap `git` and `gh` (`scripts/github-pr.sh`):

```sh
make create-branch BRANCH=<scope>/<topic>   # new branch from the latest main
make open-pr                                # push with upstream, open the pull request
make open-pr ARGS="--draft"                 # extra arguments go to `gh pr create`
make delete-branch                          # after merge: update main, delete the branch
make cleanup-repo                           # delete leftovers of closed pull requests
```

- `create-branch` checks the scope against the blueprint folders. Without `BRANCH`, or with
  an invalid one, it offers a menu of scopes and asks for the topic, which may be plain text
  such as `Dependabot integration` (turned into `dependabot-integration`).
- `open-pr` works on the current branch or `BRANCH=<name>`, without switching to it. It takes
  title and description from the commits unless `ARGS` sets them, and only prints the link if
  the pull request is already open. It refuses `main`, names outside the schema (such as bot
  branches) and branches whose pull request is already merged or closed. It never force-pushes.
- `delete-branch` works on the current branch or `BRANCH=<name>`. It only deletes a branch
  whose pull request is merged, or closed after asking, and whose commits are all part of
  that pull request. Rebase merges rewrite commits, so unpushed work is detected against
  the pull request, not against `main`.
- `cleanup-repo` removes the leftovers of merged or closed pull requests: local branches,
  and branches that only exist on GitHub. It lists them and asks first. It keeps branches
  without a pull request, the current branch, branches with commits that are not in their
  pull request and remote names outside the schema, such as bot branches.

GitHub deletes merged branches automatically. Both tasks also delete the remote branch if
it still exists, for example after a pull request was closed without merging.

## Commits and releases

Releases are managed by [release-please](https://github.com/googleapis/release-please)
in manifest mode. Each blueprint folder is its own package:

- Commits touching a blueprint folder are attributed to that blueprint only. They take no
  scope, since each blueprint has its own changelog.
- release-please opens one release pull request per blueprint. Merging it bumps the
  version line in the blueprint and the version badge in its README, updates its
  `CHANGELOG.md`, and creates the tag `<name>/X.Y.Z` with a GitHub release.
- Versions follow [SemVer](https://semver.org/) and start at `0.1.0`. `feat:` bumps
  minor; `fix:`, `refactor:`, `perf:`, `deps:` and `revert:` bump patch. A breaking change
  (`feat!:` or a `BREAKING CHANGE:` footer) bumps minor while below `1.0.0` and major from
  then on.
- Changelogs follow [Keep a Changelog](https://keepachangelog.com/) sections: `feat:` is
  listed under *Added*; `refactor:`, `perf:`, `deps:` and `revert:` under *Changed*; `fix:`
  under *Fixed*. Other types are not listed and do not trigger a release.
- A squash-merged pull request can carry several changelog entries: add one Conventional
  Commit line per extra entry at the bottom of the squash commit message.

Commit messages (or squash-merge titles) must follow
[Conventional Commits](https://www.conventionalcommits.org/), for example
`feat: add illuminance condition`. Commits outside blueprint folders may use a scope, such
as `fix(scripts): …`.

Release pull requests opened with the default `GITHUB_TOKEN` do not trigger CI. To run
checks on them, add a fine-grained token with `contents` and `pull-requests` write access
as the repository secret `RELEASE_PLEASE_TOKEN`.
